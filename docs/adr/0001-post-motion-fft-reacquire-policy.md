# Treat post-motion FFT reacquire as a shared v2 policy

Accepted. The v2 algorithm will model post-motion FFT reacquire as a shared solver-stage policy used by all algorithm presets, including TraceRescue, Lite, and dynamic-rest BO, instead of treating it as a TraceRescue-specific fix or reusing ordinary rest tracking parameters. The solver owns the stage transition logic, while presets only supply default parameters. The post-motion period has different slew-limit behavior from both the guard window and pre-motion rest, so the guard-window duration remains an experimental variable and post-motion reacquire parameters can be evaluated independently. Offline replay rejected a uniform post-guard FFT switch because it rescued high-drift samples but damaged good kaihe/bobi cases where FFT low-locked around 47 BPM while adaptive tracked the real high post-motion HR. The accepted first implementation therefore keeps the current adaptive path inside and after the guard window until a post-motion high-drift trigger fires: adaptive/final HR must exceed FFT by a configured gap and FFT must be above a configured minimum plausible HR. The first reacquire window uses weak inheritance rather than being strongly locked to the guard-window terminal HR, so a bad adaptive estimate cannot anchor the post-motion FFT path. Post-motion reacquire tracking supports asymmetric limits: conservative upward movement and looser downward movement. New reports expose explicit window-stage labels while retaining the old rest/motion/recovery window-kind field for compatibility. Evaluation reports post-motion rest metrics as the primary acceptance signal across rescue, non-regression, and full-batch cohorts, because total/rest/motion aggregates can hide failures that occur after the motion segment.
